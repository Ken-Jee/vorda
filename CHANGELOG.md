# Changelog

All notable user-facing changes to Vorda.

## 0.2.1 - 2026-11-26

### Changed

- **Named projects with unchecked packages are unknown (may affect CI):** A scan of a project you name (`vorda scan DIR`, `--root`, or the GitHub Action) now reports `unknown` (exit 2) while any of its lockfile packages outside test or example folders are not assessed, such as a `Gemfile.lock`, NuGet or PHP lockfile under the offline database. The new `not-assessed` error names the sources and, offline, says that `--online` checks them. Findings still win with exit 3. Machine scans and inventory files are unchanged: they list such packages under `not_assessed` and exit 0 when nothing is found. This reverses part of the 0.2.0 not-assessed change.
- **Strict Action on partial coverage (may affect CI):** The GitHub Action has two new outputs, `coverage` (`complete` or `partial`) and `not-assessed` (a package count). With `fail-on-findings: 'true'`, a scan with no findings where any package was not assessed fails the step (exit 2) with an annotation naming the sources. SARIF is uploaded only when `coverage` is `complete`, so a partial report can no longer close open code scanning alerts for packages it never checked. A vulnerable scan that also left a file unchecked is `partial` too, and still fails with exit 1. If you upload `sarif-file` in your own step, gate it on `coverage == 'complete'`. A scan that finds no dependency file Vorda recognizes is also `partial` in the Action (a lockfile that lists no packages is not): it uploads nothing, so an empty report cannot replace a real analysis, warns in report-only mode and fails (exit 2) in strict mode. The CLI still exits 0 for it.
- **Offline watches refresh the database (may affect CI):** In offline mode, `vorda watch install` on systemd and cron now makes the daily job run `vorda db update` before its scan (systemd adds a random delay of up to 30 minutes). A failed refresh keeps the old database and the scan still runs. The download sends no package names. Pass `--no-db-refresh` to keep the old behaviour; `vorda watch uninstall` removes the job as before. Existing installs pick this up when reinstalled. Before, an offline schedule went `unknown` for good once its database was 72 hours old.
- **Summary counts:** The scan summary counts packages checked, not packages found. When something was not assessed it reads "1 of 2 packages checked, 1 not assessed" and names the ecosystems. JSON output adds `ecosystems`, with `found`, `assessed` and `not_assessed` counts for each ecosystem.
- **Dashboard coverage:** A saved scan with `not_assessed` entries now shows as partial on Overview, the Coverage tab and Inventory, with the package count and sources, such as "1 package not assessed: offline-db:RubyGems". Before, Overview said nothing needed attention and the Coverage tab said "Coverage is complete". Host health for such hosts is at least `warning`.

### Fixed

- **Browser caches are never run:** A scan no longer runs a file it finds in a Puppeteer or Playwright cache to read its version. Those folders can be set by an environment variable, so they could point inside a cloned repository. Versions now come from the cache's metadata only; a build without it is listed under `not_assessed` with "no trusted version evidence". The first scan after upgrading rereads browser versions from disk, and Linux system browsers are looked up through the package manager at fixed system paths with an empty environment.
- **MCP tools after `vorda setup`:** Setup saves a config with no `roots`, and every MCP inventory, check and agent tool then refused to run. With `roots` unset, MCP now uses the working folder, as on a fresh state. A root outside it is still refused, and `"roots": []` still denies access.
- **`vorda fix` stays offline:** With offline mode saved, fix advice for a finding with no saved fixed version no longer fetches the advisory page; it says the detail was not fetched in offline mode. Online, it contacts only the OSV advisory API and refuses any other stored address. Fixed versions already saved still work offline.
- **Repair verification uses the saved advisory source:** `vorda repair` verified every repair online and sent the package name even when offline mode was saved. It now checks against the saved source. When the local database cannot check the repaired package, the repair stays unverified and follows the usual rollback path, never passed.
- **Scheduler bus address:** `systemctl --user` calls from `vorda watch` now pass on `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` only when they name the current user's local runtime folder and a bus inside it; otherwise both are left unset and systemctl uses its own default.
- **Arch Linux advisories:** An Arch advisory with no fix released now applies to every installed build, not only the build it lists, so a newer build of a still-vulnerable package is reported. An advisory that names no version is listed under `not_assessed` (source `arch`) and no longer marks the package as checked, so a saved finding for it stays open.

### Docs

- **One exit-code table:** README, `docs/status.md` and `docs/github-action.md` share one table of the six results (clean, finding, finding with gaps, not assessed, error, nothing to scan) with the CLI exit code, the status, the strict Action result and whether SARIF is uploaded. A test checks every row.

## 0.2.0 - 2026-11-23

### Changed

- **Machine scan by default (may affect CI):** `vorda scan` and `vorda check` with no `PATH`, `--root`, `--inventory-file`, or `--oci` now scan this machine instead of the current folder. They check OS packages (including Ubuntu, which stays labelled experimental), tools (`node`, `python3`, `bun`, `deno`, `claude`, `codex`, `gemini`, `opencode`), browsers (Puppeteer and Playwright caches only), installed apps (Windows only), and project lockfiles under the home folder (`HOME`, or `USERPROFILE` on Windows). Pass one or more bare `PATH` arguments (such as `vorda scan .`) to scan only those folders or lockfiles, the same as `--root PATH` (previously exit 64). `vorda inventory` is unchanged: it defaults to the current folder and takes optional `--root` flags instead of bare paths. Machine scans skip known cache, toolchain, download, app-data, and trash folders directly under home and do not follow symlinked folders under home (recording `skipped-folder` in `coverage_evidence.observations`, plus a warning for symlinks, instead of errors). They also raise the home walk limit to 1,000,000 entries (project scans stay at 100,000), save under their own scope separate from `--root ~`, print a machine-scan summary line, and add `"machine": true` with `scan_roots` set to the home folder in JSON. Browser design limits also move from `errors` to `not_assessed`, so browsers no longer make a scan `unknown` on their own: NVD's 119-day Chrome history window (`nvd`), browsers with "no trusted version evidence" (`chromium`), and browsers with "unknown outside limited history" (`chromium`). `coverage_evidence.status` stays `partial`, which does not retire saved browser findings on its own. A saved Chrome advisory that current NVD data shows fixed in the installed version still closes, while "unsupported Chrome applicability configuration" stays an error. `vorda watch install` with no `--root` (and no root saved earlier) now schedules a machine scan, adds `"machine": true|false` to its JSON, and leaves MCP-authorized roots in `config.json` unchanged (MCP `check` is unchanged). Passing `--root DIR` schedules a project scan and is remembered by later installs; `--machine` switches back, and combining `--machine` with `--root` exits 64. Scheduled machine scans record tools not found on `PATH` as `unseen-scheduled` in `coverage_evidence.observations` with no error. They are not counted as checked, so saved findings on those tools stay open; scheduled project scans with `--tools` keep the lookup error.
- **Not-assessed items (may affect CI):** Things Vorda cannot check by design now go into a new `not_assessed` JSON list (`{"source", "reason", "packages"}`, grouped by source and reason) instead of `errors`, so they no longer make a scan `unknown` (exit 2) on their own. This covers packages with no trusted installed version (`coverage:version`), packages from package managers with no verified advisory mapping such as Homebrew, Chocolatey, Winget, Flatpak, or Windows installed apps (`coverage:<ecosystem>`), offline-database packages outside npm, PyPI, crates.io, and Go (`offline-db:<ecosystem>`), and offline-database feeds that need the network (such as Arch, Debian, and Ubuntu security trackers, Chrome for Testing, Chrome Releases, and NVD). Browser design limits (NVD's 119-day Chrome history window under `nvd`, plus browsers with "no trusted version evidence" or "unknown outside limited history" under `chromium`) also go into `not_assessed`, so `--browsers` (online and offline) and `--os-packages` and `--tools` offline no longer make a scan `unknown` on their own; an "unsupported Chrome applicability configuration" advisory stays an error. For example, an offline scan of npm packages with no findings plus a RubyGems lockfile now exits 0 (`no-known-findings`) instead of 2 (`unknown`); pass `--online` in CI that needs those ecosystems checked. `coverage_evidence.status` is `partial` whenever `not_assessed` is not empty, so previously saved findings are not retired or marked fixed, and findings still win (`vulnerable`, exit 3). Missing or stale offline indexes for npm, PyPI, crates.io, or Go, offline lookup bounds, unreadable files, failed online lookups, and the feed time budget stay in `errors` and still report `unknown`. The text summary prints a separate not-assessed block after errors and "Not checked", saved scans store `not_assessed` in the local `scans` table, and the dashboard Inventory page appends the count to a machine's line when non-zero. Saved health rows from earlier scans for these cases (for example "No advisory feed covers ... yet" on the dashboard) close on the next scan because the source no longer reports an error.
- **Experimental hub on Windows:** `vorda link migrate`, `vorda link restore`, and `vorda link serve` no longer fail on Windows with os error 33 or os error 5. The hub stays experimental. They lock a separate `<database>.db-lock` file beside the database instead of the SQLite database file itself. This avoids Windows mandatory lock failures (os error 33) while still stopping two operations from running at once. The lock file is created on first use (mode 0600 on Unix). On Windows, migrate and restore also skip the folder flush step because Windows cannot open a folder that way (which failed with "Access is denied", os error 5), and Unix still flushes the folder.
- **Microsoft Store `python3` stub (may affect CI):** On Windows, `--tools` now counts a tool in `%LOCALAPPDATA%\Microsoft\WindowsApps` as not installed (an observed absence) only when its `--version` run fails with the stub's own message "Python was not found". Stock Windows puts a Store app alias for `python3.exe` in that folder that prints that message on stderr and exits 9009. Previously `--tools` reported this as an inventory error and made the scan unknown (exit 2), so a scan that was unknown can now be complete. A timeout, a failure to start the program, or any other failure stays an inventory error, so the scan stays unknown. On Windows set to another display language the stub's message differs, so it also stays an error. A working Store-installed Python in the same folder is still checked as before.
- **Windows state folder:** New installs on Windows now default to `%LOCALAPPDATA%\vorda\state` instead of `%USERPROFILE%\.local\share\vorda`. If `%USERPROFILE%\.local\share\vorda` already exists, Vorda keeps using it, so nothing is moved and existing scans, mailbox, and settings stay. `--state DIR` and `VORDA_HOME` still override it, and Linux and macOS keep `~/.local/share/vorda`. The offline advisory database location (`%LOCALAPPDATA%\vorda\advisory-db`) is unchanged and stays outside the state folder.
- **Test and example folders (may affect CI):** Files Vorda cannot check (unsupported formats, manifests without a lockfile, unreadable or malformed lockfiles, or lockfiles with uncheckable entries) no longer turn a scan into `unknown` (exit 2) when they sit in a folder named `test`, `tests`, `testdata`, `__tests__`, `__fixtures__`, `fixtures`, `example`, or `examples` (any letter case) below the scan root. They are instead listed in `warnings` (collapsed to one line on stderr when there are two or more) and in `coverage_evidence.observations` with kind `not-covered-test-data`, and `coverage_evidence.status` is `partial` so nothing previously saved from those files is retired or marked fixed. Readable lockfiles in those folders are still read and checked, with their packages marked likely dev-only (previously only lower-case `fixtures`, `test`, and `tests` were). Scanning one of those folders directly with `--root` still checks it strictly, and `--exclude PATH` still leaves a path out entirely.
- **Go standard library:** Vorda no longer lists a `stdlib` package from `go.mod`, from either the `go` line or the `toolchain` line, so it reports no Go standard library findings from `go.mod`. Both lines name minimums while the Go release that builds the program can be newer, which produced false alarms (139 standard-library findings on two repositories that no other scanner reported; osv-scanner 2.7.1 also lists no `stdlib` package for a `go.mod` with either line). The inventory JSON fields `version_basis: "go-directive-minimum"` and its `note` are removed. The `go` line is still read to decide whether `go.mod` lists the whole build (Go 1.17 or later), and `vorda fix` still suggests `go get toolchain@go<version>` for a `stdlib` finding from another inventory source.
- **RubyGems platform builds:** For `Gemfile.lock` entries with platform suffixes (such as `nokogiri (1.13.10-x86_64-linux)` and `nokogiri (1.13.10-arm64-darwin)`), Vorda now reads the version before the first `-` and lists each gem version once, so one advisory is reported once per gem version instead of once per platform build (144 repeated findings on one repository before).
- **PEP 751 `pylock.toml` lockfiles:** Vorda now reads `pylock.toml` and `pylock.<name>.toml` (where `<name>` has no dot), which previously reported as unsupported and made scans `unknown`. Root `lock-version` must be the string `1.0`. Each `[[packages]]` entry with a `name` and `version` and no `vcs`, `archive`, or `directory` source is checked as a PyPI package without evaluating markers (`marker`, environments); `vcs`, `archive`, and out-of-project `directory` sources are listed as uncheckable, an in-project `directory` without a `version` is skipped as first-party code, and an in-project `directory` with a `version` is queried by name and version. An empty `packages` array stays `unknown`, a `pylock.toml` beside `pyproject.toml`, `setup.py`, or `setup.cfg` covers it, and native capture also accepts `pylock.toml` and `pylock.<name>.toml` inputs.
- **Requirements folders (may affect CI):** `.txt` and `.in` files containing requirement lines anywhere under a `requirements` folder inside the scan root (for example `requirements/base.txt`, `requirements/dev.txt`, or `requirements/production/web.txt`) are now read like `requirements.txt` instead of being reported as unsupported. Exact pins (`==`, `===`) are checked, unpinned lines are listed as not checked (not covered) and keep the scan `unknown`, `-r`/`--requirement` rejects the file, `-e` lines and direct references are uncheckable, and pip option lines (`-i`, `--index-url`, `-f`, `--pre`, `--require-hashes`, `-c`, and similar) are skipped. Prose files with no requirement or option lines (such as `requirements/README.txt`) are still ignored, `constraints*` files are still skipped, and the unpinned-line hint now names the real file (for example `uv pip compile base.txt`). Native capture still accepts requirements inputs by `requirements*.txt` name only.
- **Uncompiled `requirements*.in` files (may affect CI):** `requirements*.in` files (for example `requirements.in` or `requirements-dev.in`) are now read when no compiled file sits beside them instead of being reported as unsupported. Exact pins are checked and unpinned lines are listed as not checked (not covered), so the scan stays `unknown` until they are pinned or compiled. A `.in` file (including one inside a `requirements` folder, such as `requirements/base.in` beside `requirements/base.txt`) is skipped in favour of a compiled file beside it only in two cases. First, the same stem with `.txt` sits beside it and Vorda reads that `.txt` (a `requirements*.txt` name, or a requirements-folder `.txt` with requirement lines; a `dev-requirements.txt` beside `dev-requirements.in` does not count because Vorda does not read that name). Second, a `pylock.toml` or `pylock.<name>.toml` in the same folder reads cleanly and lists every package the `.in` names (names compared after lower-casing and treating `-`, `_`, and `.` alike). If the `.in` has any line that is not a plain requirement (an option such as `-r` or `-c`, a URL, a path, or a direct reference with `@`), or names a package no pylock there lists, a pylock does not skip it and the `.in` is read. When skipped, the compiled file is read instead. Outside a `requirements` folder, `*-requirements.in`, `*_requirements.in`, `*-requirements.txt`, and `*_requirements.txt` are still reported as unsupported.

### Added

- **Guided first-time setup (`vorda setup`).** Lets you choose offline (default) or online advisories, saves the choice in `config.json`, downloads the local database when offline (25 to 80 seconds, about 190 MB in `~/.cache/vorda`), optionally installs scheduled hourly and daily machine scans (default no), and runs the first machine scan. Accepts `--offline-db`, `--online`, `--watch`, and `--no-watch`; outside a terminal or in CI a mode flag is required or setup exits `64`. Running bare `vorda` in a terminal before any mode is saved starts setup, otherwise it prints help; run `vorda setup` again anytime to change the mode.
- **Self-updater (`vorda update`).** Updates the running executable from the latest signed GitHub release by verifying `SHA256SUMS.minisig` against the built-in release key (key ID `57E5204A70E3811B`, not overridable by files, URLs, or environment variables), checking the executable's SHA-256 and `.minisig`, swapping it into place while keeping the previous binary as `vorda.old`, running the new binary with `--version` (rolling back if that fails), and running `vorda db update` when offline mode is saved. Supports `--check` to report status without changing files and `--version VERSION` to install a specific release, including older ones. Refuses package-manager installs, development builds, and unsigned releases without changing anything; exits `0` when updated, up to date, or after `--check`, `2` on errors or rollback, and `64` on usage errors, or with the exit code of `vorda db update` when it refreshes the offline database.
- **Signed release artifacts.** v0.2.0 is the first signed release: every executable ships with a `.minisig` file and `SHA256SUMS` ships with `SHA256SUMS.minisig`, signed with the Vorda release key (minisign key ID `57E5204A70E3811B`, public key in `rust/release/vorda-release.pub`). Release executables embed that public key so `vorda verify-self` verifies the installed binary against `vorda.minisig` beside it (v0.1.0 and v0.1.1 were unsigned).
- **Executable signature checks in `install.sh` (may affect CI).** When `minisign` is on `PATH`, the installer now requires and verifies both `SHA256SUMS.minisig` and the executable's `.minisig` with the release key before installing, exiting `1` without installing if either is missing or bad; without `minisign`, it checks SHA-256 only as before. It also saves the executable's signature beside the binary as `vorda.minisig` when the release includes one, so `vorda verify-self` reports `verified` right after install. The installer now ends by printing `Next: run vorda setup ...` and does not run setup itself.
- **Dashboard redesign.** Light theme with six pages (Overview, Findings, Inventory, Inbox, Repairs, and Policy), phone layouts at 390 px width, and 404 responses for removed routes. Findings adds tabs (All findings, Known exploited, Needs review, Uncertain coverage) and a detail card for the selected finding, moving scan-health rows out of finding counts into Uncertain coverage. Inventory adds tabs (Machines, Projects, Browsers, Agent tools) and a coverage card; Inbox shows open mailbox messages read-only (with exactly one mailbox reader, it follows that reader's view so acknowledged and snoozed messages drop out, as `vorda mail list` does); Repairs holds repair drafts (moved out of Inbox) with Proposed change and Safety conditions panels; Policy shows fleet mode controls, machine and agent rules, and protected items.
- **Per-page dashboard empty states before the first scan.** Each dashboard page renders its own empty state before any scan has run instead of one shared placeholder, without writing to the state folder. Unknown paths return 404.

## 0.1.1 - 2026-11-22

### Changed

- **Exit code change (may affect CI):** A scan that finds vulnerabilities now reports `vulnerable` (exit 3) even when some files could not be checked or a lookup failed; previously any error turned the status and exit code into `unknown` (exit 2), which masked the vulnerable result even though findings were still listed. Errors and skipped files are still listed, `coverage_evidence.status` stays `partial`, and scans with no findings still report `unknown` (exit 2) when errors or skipped files occur.
- **Alert delivery failures (may affect CI):** A failed alert delivery (webhook, ntfy, or desktop) no longer turns a `vulnerable` result (exit 3) into `unknown` (exit 2).
- **Empty folder scans (may affect CI):** Scanning a folder with no recognized dependency files now reports `no-known-findings` with 0 packages (exit 0) and prints a "Nothing to scan" notice to stderr. Scans that also request `--os-packages`, `--tools`, `--browsers`, `--installed-apps`, `--installed-root`, or `--oci` and find nothing still report `unknown` (exit 2).
- **Dashboard login token (may affect services):** The dashboard login token is printed only when stdout is a terminal. Outside a terminal (for example, a systemd unit), `vorda dashboard --token` and `--allow-writes` require `VORDA_DASHBOARD_TOKEN`; without it they exit 64 and print nothing on stdout. When stdout is not a terminal, the dashboard URL is printed without the token so the token never reaches service logs. Anyone running the dashboard as a service with a generated token must set `VORDA_DASHBOARD_TOKEN` before upgrading.
- The findings summary is sorted by urgency: the header shows counts by priority and a dev-only count; up to eight package lines are ordered by priority, known-exploited status, runtime before dev-only, then name, prefixed with `[critical]` through `[unrated]` and `; dev-only` when every finding is in a likely dev-only package. Skipped files appear under a separate "Not checked" heading.
- "fixed in" versions now show only versions above the installed one, kept to its release line when the advisory has a fix there, lowest first (for example, `body-parser` 2.3.0 shows `2.4.0` instead of `1.20.9, 2.4.0`). Applies to npm, PyPI, crates.io, and Go; other ecosystems keep feed order.
- Unpinned `requirements.txt` lines now show the line number, the package name, and how to fix it (pin the version or use a lockfile) instead of `"line 4"` as the package name.
- `vorda verify-self` on an unsigned build now states that Vorda does not sign releases yet and points to `--pubkey FILE` instead of saying "Development build". Exit code 2 and status `unsigned` are unchanged.
- The scan summary note about saved findings explains that `mail --reader NAME` takes any label and keeps state per reader.
- The first-run setup prompt and docs now match on the offline database download estimate: 25 to 80 seconds and about 190 MB in `~/.cache/vorda`.
- When two or more symlinked folders are skipped because their targets are already scanned, the warning is now one line (`--json` still lists each one).
- The GitHub Action now logs scan errors whenever there are any.
- Renamed the `ci_helper` build manifest schema ID to `vorda-candidate-v1`.

### Added

- `--exclude PATH` (repeatable) skips a file or folder under the scan root. Excluded paths are listed in the summary and JSON `excluded` field, and scans with `--exclude` are saved under their own scope so they never close findings from a full scan. If an excluded path is never reached, Vorda warns and treats the run as a full scan; another spelling of the same path (such as a trailing slash or a lower-case Windows drive letter) still counts as reached.
- Support for multi-document `pnpm-lock.yaml` (pnpm 11 and later; each document must be `lockfileVersion` 6.0 or 9.0, and duplicate packages are read once), `uv.lock` revisions 4 and 5, and Yarn Berry `yarn.lock` with `__metadata` version 10. Previously these failed as `unknown` with no results; measured with the benchmark harness on three public projects, comparing v0.1.0 with this release raised detection from 0 of 38 known advisories to 38 of 38.
- `install.sh` accepts `VORDA_INSTALL_FROM=DIR` to install from a local folder holding `SHA256SUMS` and the release executables without `curl` or `wget`, while still checking the SHA-256 checksum.
- Findings JSON adds a `summary` field. Advisories without a fixed version show their summary (for example, "chrono is unmaintained") when the package has exactly one advisory. Summary text changes do not mark saved findings as changed or trigger repeat notifications.
- `vorda --help` now includes `"To start, cd into a project and run vorda scan"`.
- `benchmark/` adds a reproducible comparison against osv-scanner 2.7.1, Trivy 0.76.2, and Grype 0.122.1, with 2026-11-22 results in `benchmark/results/` (the test corpus is not published). Vorda had no false clean result in any run, and the results list every place Vorda found less than the other tools.
- Scan JSON error entries can carry a `not_covered` flag, and `vorda inventory` JSON gains a `coverage_gaps` list.

### Fixed

- Windows source builds (no Windows release executable yet): fixed mixed `/` and `\` in the Chrome path, accepted plain roots such as `D:\work\app` in `vorda capture`, and fixed compilation of the test suite on Windows.
- `vorda inventory` on an empty folder now exits 0 (documented in `docs/reference.md`).
- MCP servers and link payloads now report the actual Vorda version instead of a fixed `0.1.0`.

### Docs and repository

- `rust/src/scanner/fixtures/README.md` states that fixture files are deliberately vulnerable test data and must never be installed.
- `.github/dependabot.yml` skips the test fixture folders so Dependabot does not open pull requests to update deliberately vulnerable test data.
- Regenerated README example output from a real run.

## 0.1.0 - 2026-11-22

First public release. Ships unsigned static Linux executables for x86_64 and arm64, an installer script (`install.sh`), and SHA-256 checksums (`SHA256SUMS`).
