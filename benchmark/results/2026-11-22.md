# Scanner benchmark, 2026-11-22

This benchmark compares Vorda v0.1.0 with osv-scanner 2.7.1, Trivy 0.76.2, and Grype 0.122.1. Each tool ran one at a time in its default online mode and in an offline mode inside a network namespace with no network. The 50-target corpus contains 16 hand-written lockfiles across 11 ecosystems (53 vulnerable package versions, 589 advisories, and one clean control each), 20 public repositories cloned read-only at pinned commits with depth 1, 8 manifest-only projects with no lockfile, and 6 public container images saved as archives; nothing in the corpus was installed or run.

## Verdict

Vorda v0.1.0 is not yet a replacement for osv-scanner, Trivy, or Grype. Today, osv-scanner finds more on lockfiles and manifests: it hit 589/589 (100%) ground-truth lockfile advisories online and offline, 972/990 (98%) on real repositories online, and 150/253 (59%) on manifest-only projects online. Vorda hit 500/589 (85%) on ground-truth lockfiles online (351/589, or 60%, offline), 767/990 (77%) on real repositories online (632/990, or 64%, offline), and 4/253 (2%) on manifest-only projects. On container images, Grype, osv-scanner, and Trivy all find more than Vorda: Grype found 966/1070 (90%) agreed CVEs online, osv-scanner found 836/1070 (78%) online and 835/1070 (78%) offline, and Trivy found 735/1070 (69%), putting Vorda last at 533/1070 (50%) online and 0 offline. Vorda is the only tool that never answered "clean" when it could not check something, with 0 false cleans across all 50 targets in both modes. By contrast, Trivy and Grype each gave false cleans on 6 of 8 manifest-only projects, Grype gave 2 on real repositories (mastodon and spring-petclinic), and osv-scanner and Trivy each gave 1 offline (spring-petclinic).

## Where Vorda loses

1. Vorda rejects several current lockfile formats, skipping the whole lockfile and reporting unknown for the repository. This happened on pnpm lockfiles with more than one YAML document (vite), `uv.lock` revision 5 (djangoproject.com), and Yarn 4 lockfiles with `__metadata` version 10 (mastodon). These are the formats today's default tool versions write.
2. Vorda does not read four entire ecosystems: Maven (`pom.xml`, `build.gradle`, `gradle.lockfile`), Pub (`pubspec.lock`), Hex (`mix.lock`), and Swift (`Package.resolved`). It found 0 of the advisories in those four ground-truth lockfiles and reported unknown rather than clean. It also does not read `pylock.toml`, `requirements.in`, `deno.json`, or pinned requirement files with other names such as `requirements/prod.txt`.
3. Offline mode covers only npm, PyPI, crates.io, and Go. NuGet, RubyGems, Packagist, and all OS packages report unknown offline. Ground-truth recall drops from 500/589 (85%) online to 351/589 (60%) offline, while osv-scanner (589/589, 100%), Grype (579/589, 98%), and Trivy (576/589, 98%) stay at 98 to 100% offline.
4. In container images, Vorda is last behind all three other tools at 533/1070 (50%) agreed CVEs online and 0 offline, against 966 (90%) for Grype, 836 (78%) online and 835 (78%) offline for osv-scanner, and 735 (69%) for Trivy. Vorda reads OS packages only and skips Go binaries (16 packages seen in traefik against 256 for the other tools) and language packages (for node:14-alpine, Vorda saw 17 packages against 478 for Trivy and Grype; osv-scanner also saw only 17). It found 9 Debian 10 CVEs where Grype found 80 and Trivy found 38. On Ubuntu 20.04 it stopped at unknown because it could not parse Canonical's CVE tracker data, and offline every image reports unknown.
5. Vorda does not resolve transitive dependencies from manifests, so `package.json`, `pom.xml`, `Cargo.toml`, `Gemfile`, `composer.json`, `.csproj`, and `pubspec.yaml` without a lockfile all report unknown. Online, osv-scanner resolves `pom.xml`, `requirements.txt`, and `.csproj` and hit 150/253 (59%), while Vorda hit 4/253 (2%). On a top-level `requirements.txt`, Vorda reported the listed package and missed 2 vulnerable transitive packages (urllib3 and idna) without saying the result was partial.
6. Vorda returned noisy unknowns on 14 of 20 repositories online. On poetry, flask, and composer, a test fixture or example manifest without its own lockfile made Vorda answer unknown. On jellyfin, its real `.csproj` projects have no lockfile and Vorda does not read `.csproj` (osv-scanner does). On pipenv, it is unknown mainly because of `pylock.toml`. A CI job gets exit 2 on these repositories even when the main lockfile was fully checked.
7. Vorda reported 139 Go standard library findings across the Go repositories from the `go` directive, which no other tool reports. Because the `go` line is a minimum version, these are false alarms whenever a newer Go toolchain builds the code.
8. Vorda reports a RubyGems package once per platform build. On railsgoat, nokogiri 1.19.0 and sqlite3 2.9.0 appear with nine platform variants each, giving 144 repeated findings. Grype repeats them the same way (144); osv-scanner and Trivy report each once.

## Where Vorda wins or ties

- Never a false clean: across all 50 targets and both modes, Vorda never answered clean when it could not check something. Every gap listed above shows up as unknown with the file and reason named.
- Full recall on the lockfile formats it reads: Vorda hit 100% of advisories online on npm, PyPI, crates.io, Go, NuGet, RubyGems, and Packagist lockfiles, with 0 false alarms (every tool had 0 false alarms on the ground truth; Trivy also reported 7 unverified extras). Trivy missed some Go, PyPI, crates.io, Packagist, and Hex advisories; Grype missed some PyPI, crates.io, and Hex advisories.
- Second on real repositories online: Vorda hit 767/990 (77%), behind osv-scanner (972/990, 98%) and ahead of Grype (534/990, 54%) and Trivy (446/990, 45% online and 482/990, 49% offline). Note that Trivy skips npm dev dependencies by default.
- Smallest offline database: 176 MB downloaded in 30 seconds, against 1.2 GB for osv-scanner, 3.4 GB for Trivy (about 40 seconds), and 3.6 GB for Grype (about 60 seconds).
- Fast online lockfile scans: 9 seconds for all 16 ground-truth lockfiles online, against 24 seconds for Grype and 32 seconds for osv-scanner. Trivy was fastest at under 2 seconds.

## How to read the tables

- **Advisories hit**: the tool reported the advisory, by any of its ids or aliases, on the right package.
- **Silent misses**: vulnerable packages missed while the tool still gave a definite answer.
- **False alarms**: an advisory OSV holds for that package but says does not affect that version, or a withdrawn advisory.
- **Unverified extras**: an advisory id OSV does not hold for that package; not counted either way.
- **False clean**: the tool answered clean on a target with known vulnerabilities.
- **Unknown**: the tool said it could not finish (Vorda exit 2, osv-scanner exit 128).
- **Errors**: the tool failed.
- **Can't scan**: the tool saw none of the target's labelled packages.
- **Agreed CVEs**: CVEs at least two tools reported for the same image online.

## Caveats

- Labels come from OSV.dev and the GitHub Advisory Database, with transitive dependencies for manifest-only projects resolved through deps.dev. Vorda and osv-scanner both use OSV data, which favours them on recall, while Trivy and Grype use their own databases.
- On manifest-only projects, osv-scanner resolved some transitive packages to different versions than the deps.dev labels (for example, urllib3 1.26.9 instead of 1.26.20); advisories it reported on its own versions are counted as unverified extras, not false alarms.
- Real-repository recall is measured against OSV advisories for the union of packages any tool saw, not against a complete truth.
- Image scores measure agreement between tools, not ground truth. Because osv-scanner names Debian and Ubuntu packages by source package, only CVE ids are compared.
- osv-scanner and Trivy cannot open an OCI image archive, so they were given the same images as Docker archives.
- Maven Central rate-limited this machine (HTTP 429) after osv-scanner and Trivy resolved `pom.xml` files online, so Trivy's three online Maven runs failed. Its offline runs on those targets are included.
- Labels and databases are a snapshot from 2026-11-22. Results change as advisories are published.
- Snyk CLI was left out because it needs an account.
